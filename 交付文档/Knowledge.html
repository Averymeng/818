《Knowledge》—— AI / Agent 搭建方法论笔记

来源：2026-08-18 项目讨论中出现的知识困惑点，整理为方法论笔记（非问答）。

一、Agent 的五大组成与地基

组成部分本项目中的对应一句话理解
LLMDeepSeek推理引擎（大脑）
PromptSystem Prompt + 各节点提示词规则说明书：你是谁、做什么、输出什么、禁止什么
Memory本次诊断的中间结论与上下文过程记忆，不是长期用户偏好
知识库（≈RAG 数据源）案例库（case 表）可检索的历史资料
Tools12 个工具（取数/计算/规则/检索）模型可调用的外部函数
数据库（SQLite）全部数据的持久化不属于五大组成，是承载一切的地基
  • SQLite 是单文件嵌入式数据库，适合 Demo 与可复现场景；未来生产化可平移到 PostgreSQL（JSON 列升 JSONB）。

二、代码与 LLM 的分工原则

原则：代码负责确定性的"手和眼"，LLM 负责判断性的"脑"。

  • 必须由代码做：指标计算、数据查询、阈值规则、权重排序、贡献拆分
  • 必须由 LLM 做：下钻顺序决策、原因解释、案例差异比较、建议生成
  • 铁律：LLM 永不心算。任何数字必须来自工具返回值，否则必然产生幻觉数字

编排示例：LLM 说"检查本周新计划的计划级 CTR"（决策）→ 代码工具 get_daily_metrics 返回数据（执行）→ LLM 读结果决定下一步（再决策）。

三、什么是"编排"（Orchestration）

  • 编排 ≠ 多 Agent 协作。单个 Agent 内部也有十几个步骤（取数→扫描→下钻→生成），这些步骤的执行顺序、状态传递、停止条件需要用代码接成流程，这就是编排
  • 类比：一个员工也需要 SOP
  • 多 Agent 是另一个概念（多个 LLM 角色分工协作），本项目不需要
  • 选型：自研轻量 Python 节点图即可，不必上 LangGraph/LangChain

四、RAG 是什么、何时搭、在本项目中的形态

  • 是什么：检索增强生成——先从知识库检索相关内容，再交给 LLM 参考；不是联网搜索
  • 本项目形态：历史案例库检索（search_cases 工具）
  • 何时搭：Agent 基础链路跑通之后（知识库需要先有内容，先搭 = 搭空书架）
  • 技术选型：几十到几百条案例用 SQLite + 文本匹配足够，不需要向量数据库
  • 算不算工具：算。RAG 在项目中以工具形式暴露给 LLM 调用

五、Prompt 的正确开发流程

  • 手写第一版 System Prompt（基于业务规则文档）
  • 喂模拟数据跑一遍，让 LLM 生成诊断结果
  • 人工审查：幻觉、错误归因、不可执行的建议
  • 修改 prompt（加约束、加示例、定格式）
  • 重复 2-4 直到典型场景干净跑通
  • 稳定后封装为可复用模块/skill

反模式：让 LLM 自己生成自己的 prompt；prompt 没经过运行验证就封装。

六、数据层设计（最易混淆的一组概念）

两个不同的东西，必须区分：

概念所属侧含义本项目结论
异常标签系统输出侧给诊断出的异常事件打什么标签已简化（排序即严重度，砍四级标签）
数据场景覆盖数据侧模拟数据里构造正常/单点异常/复合异常/数据缺失客户必须保留（PRD 验收要求三类场景跑通）
  • "参数化注入"：生成数据时用参数控制（哪个客户/哪天/哪个指标/变多少），保证可复现、评测能对答案
  • 模拟数据 = 开发、评测、上线演示共用的同一批版本化数据（sim_version），禁止运行时临时随机生成
  • 部署的 Demo 平台预置这批模拟数据，不会空空如也

七、评测的启动时机

  • 不是"搭完且完美之后"才评测。正确节奏：Agent 能端到端跑通 → 立即建评测集 → 跑分 → 按结果优化 → 循环
  • 评测驱动优化，不是装饰性收尾
  • 评测 ≠ 产品功能：审核动作、案例状态属于产品运行闭环；评测是离线测试 Agent 质量
  • 交点：线上 Badcase 与驳回记录可沉淀为评测回归用例

八、证据约束：断言 vs 建议

  • 归因断言：必须引用数据证据；数据不足时只能写"待验证假设"，不能写成事实
  • 优化建议：不受数据约束——可以建议用户排查/采集任何东西（如首响时长、客服话术），给足让用户自己挑
  • 方法论推断（人教给 Agent 的经验规则）合法，但须标注"推断"，不得伪装成数据结论
  • 取消某个数据字段 ≠ 取消对应归因能力；边界在"事实断言 vs 参考推断"

九、正负向归因方法论

共享定位引擎（同一套代码、同一个顺序）：规则检测 → 贡献拆分（版位→计划→笔记，取最大贡献者）→ 基建检查。到此处为止正负向零差异，分叉在解释层：

维度负向归因（修复）正向归因（放大）
目标定位损坏环节并修复确认改善真实、可持续、可复制
特有步骤漏斗串联定位损坏环节①基建检查（是否客户主动扩量）②排除数据质量假象 ③可持续性判断 ④提炼可复制组合+扩量止损线
解释问题哪里坏了、怎么修是不是真的、能不能持续、能不能复制
  • 正向不是负向的简单取反

十、需求锁定的工程习惯

  • prompt 管内容，页面管样式：颜色、图标、布局归前端阶段；prompt 只保证输出结构化字段
  • 只改被点名的部分：未点名的内容默认已认可，不得顺手优化
  • 前端放最后：Agent 跑通、评测达标后再动页面
  • 部署 Demo 预置版本化模拟数据 + 预留用户上传通道，不接真实公司数据源

十一、常见认知偏差（自查清单）

  • 把 RAG 当先行模块——它依赖 Agent 与知识库内容，应排最后
  • 以为 prompt 可以脱离工具/数据独立先写——prompt 必须引用工具规格与输出结构
  • 把搭建当一次性工程——实际每阶段建完立即验证（数据抽查/工具单测/场景试跑）

十二、本地观察 Agent 运行的方式

  • tmux attach -t <会话名>：进入实时终端看命令行滚动，Ctrl-b 再按 d 退出观看，不影响运行
  • tail -f <日志文件>：跟随日志流，更简单
  • 本地浏览器界面：展示阶段进度、工具调用流与输出（Streamlit/Gradio 等）
  • 关键认知：Agent 在本机执行时，输出可同时进终端、日志文件和浏览器，三者不冲突
