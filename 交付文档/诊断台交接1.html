《诊断台交接1》—— 客户投放经营与复盘 Agent 项目定稿文档

本文档是当前项目的最高优先级依据，整合自三份来源：①PRD V0.1（客户投放经营与复盘Agent_PRD_Demo_V0.1.docx）②交接说明 V0.2（AI商业化销售复盘Agent项目交接说明_V0.2.docx，冲突处以它为准）③2026-08-18 设计讨论定稿（与 V0.2 冲突时以讨论定稿为准）。任何新接手的 Agent 读完本文档即可开始搭建，无需回读原文档。

一、项目定位

  • 名称：小红书线索投放经营与复盘 Agent（内部称"诊断台"）
  • 一句话定位：为广告平台商业化销售打造的小红书线索投放周度复盘工作台——销售选定一个客户，Agent 自动完成全层级扫描、异常定位与下钻、证据化归因，生成可审核的结构化网页报告，人工确认后沉淀为可复用案例，并支持离线评测与回归
  • 用户：商业化销售，单角色，只读诊断（AI 一切只建议、绝不自动执行任何账户操作）
  • 用途：周度复盘（深诊）+ 日常监控（雷达）
  • 部署：最终部署到公开网络，定位为展示 Demo + 面试演示；不接入任何真实公司数据源；部署动作在离线评测通过之后进行

四、指标口径

4.1 原始字段（入库字段）

客户ID/名称、行业、赛道、品类；日期；版位、计划ID/名称/创建日期/状态/日预算；笔记ID/标题/素材形式/创建日期/状态；优化目标、目标优化成本；消耗、曝光、笔记点击量、按钮点击量、私信开口量、留资量。

4.2 派生指标（9 个，运行时确定性计算，不入库）

指标公式含义
CPM消耗÷曝光×1000流量价格
CTR笔记点击量÷曝光标题与封面整体吸引力
CPC消耗÷笔记点击量笔记点击成本
按钮点击率按钮点击量÷笔记点击量笔记内容对私信动作的承接
私信开口率私信开口量÷按钮点击量进私信后是否愿意开口
链路留资率留资量÷私信开口量客服回复速度与话术承接
留资CVR留资量÷笔记点击量点击到留资端到端转化
开口成本消耗÷私信开口量目标=开口时的核心成本
留资成本消耗÷留资量目标=留资时的核心成本

4.3 对比与时间基准

  • 周复盘 = 本周 vs 上周（对比周固定为上周，销售不选）；比例类指标加权汇总对比；版位占比用百分点 pp
  • 日监控 = 昨日 vs 近 14 天加权基准
  • 版位结构是否异常只看客户自身历史，不存在固定最佳占比

4.4 基建双门槛

  • 在投计划变化 ≥2 个 且 相对变化 ≥20% 判异常
  • 在投笔记变化 ≥5 篇 且 相对变化 ≥20% 判异常
  • 新投计划/笔记还须看是否获得足够曝光/点击

五、异常与归因体系（定稿）

5.1 标签体系（已简化）

  • 不设独立四级严重度标签：40/30/20/10 权重排序本身就是连续严重度；报告分级词从排序派生（Top3=重点归因，其余=观察项）
  • 位置 = 异常事件固有字段（规则触发时天然携带：指标+版位/计划/笔记），零额外成本
  • 方向 = 指标变化正负号，免费保留
  • 异常形式（单指标/链路组合/指标冲突/结构变化/数据质量）= 可选下钻提示，非必填
  • 数据不足标记 = 异常分支开关：仅完整性检查不通过（缺天/样本不足）时打上，非常态；作用是命令该层不许下硬结论

5.2 排序与 Top3

权重 = 消耗影响 40% + 优化目标成本贡献 30% + 异常幅度 20% + 数据置信度 10%。报告只重点归因 Top 3，其余进观察项/附录。

5.3 八条异常→建议映射（规则底座）

  • 消耗下降 → 查基建（在投计划/笔记是否减少）→ 建议补量
  • CPM 上涨 → 查版位结构变化（pp）→ 调整预算结构
  • CTR 下降 → 查标题与素材形式（封面归因只能作待验证假设/方法论推断）
  • 按钮点击率下降 → 查内容承接、新旧笔记差异
  • 私信开口率下降 → 查私信入口与首响
  • 链路留资率下降 → 查话术与回复速度，建议与客户确认
  • 优化目标成本上涨 → 从成本反向拆最大贡献环节
  • 成本下降且消耗上升（正向）→ 提炼可复制组合 + 小幅扩量 + 成本回退阈值止损

5.4 归因方法与证据约束

  • 先沿漏斗串联定位问题，再按版位/计划/笔记并联拆分
  • 归因断言必须引用证据；数据不足的归因只能写"待验证假设"
  • 优化建议不受数据约束：可建议排查/采集任何东西（如首响时长、话术），给足让用户挑
  • 方法论推断（人教过的经验规则）合法，但须标注"推断"，不得伪装成数据结论；取消字段 ≠ 取消归因能力

5.5 正负向归因（共享引擎 + 分叉解释层）

共享定位引擎（同一套代码、同一顺序）：规则检测 → 贡献拆分（版位→计划→笔记，取最大贡献者）→ 基建检查。

维度负向归因正向归因
目标修复放大/复制
解释层步骤漏斗串联定位损坏环节 → 修复建议①基建检查（是否客户主动扩量，最常见解释）②排除数据质量假象（缺天数让成本"看起来变好"）③可持续性判断（新笔记爆发效应？一次性活动？）④提炼可复制组合 + 扩量止损线
回答的问题哪里坏了、怎么修是不是真的、能不能持续、能不能复制

5.6 报告整体状态（overall_status）派生规则

Top3 构成整体状态
无异常事件正常
只有观察项、或异常均为轻微/正向需关注
存在显著负向异常需行动

六、触发机制（定稿）

6.1 周度复盘（主动触发）

  • 销售只选客户 + 触发；对比周固定 = 上周，界面无选择项
  • 上周数据缺失超门槛 → 入口直接拦截提示"上周数据不足，无法对比"，不让改选其他周
  • 产出：八章节完整报告

6.2 日常监控（被动触发）

  • 系统每日扫描全部客户昨日数据：昨日 vs 近 14 天加权基准
  • 阈值：优化目标成本 ±20% 或消耗 ±30% 触发卡片；每客户每日最多 1~2 张
  • 仅登录后展示，不推送、不发邮件/SMS
  • 卡片 0 个 LLM 调用，全部代码规则生成（LLM 只用于周度复盘下钻）

监控卡片结构（定稿版）：

卡片行内容
客户客户名 · 行业/赛道 · 优化目标
详情昨日消耗 | 目标量（留资/开口数）| 目标成本
异动日期 | 指标偏离幅度（vs 近14天加权基准）| 阈值
归因最大贡献对象及贡献百分比（代码贡献拆分的初步归因，深度归因在周报）
提示1~2 条一句话建议（规则模板生成）
操作转周度复盘 | 看近14天趋势 | 转待办

6.3 告警（远期可选，MVP 不做）

  • 部署定位为纯展示 Demo + 测试用户，维持"仅登录展示"即可
  • 若后加：最多站内通知（红点+通知列表），频控每客户每日 1 条，静默时段；webhook/邮件不做

七、报告（定稿）

7.1 八章节结构

  • 封面：客户 · 行业/赛道/品类 · 周期（本周vs上周）· 版本 · 生成时间
  • 核心结论：整体状态（正常/需关注/需行动，规则派生）+ 3~5 句总述 + Top3 异常一览
  • 指标与趋势：9 项指标卡（带环比）+ 漏斗（曝光→点击→按钮→开口→留资）+ 14 天趋势
  • 分层诊断：版位/计划/笔记/漏斗四层，各层状态 + 关键证据
  • 异常与原因：Top3 逐条（现象→证据→归因→置信度），其余折叠为观察项
  • 案例参考：相似案例 + 关键差异（Badcase 不可引用、不出现）
  • 优化建议：每条含依据/优先级/风险/预期观察指标
  • 行动计划：动作/负责人/时间/预期指标

7.2 输出形式

  • 报告以结构化 JSON 存储，网页 Onepage 渲染为 MVP 优先
  • Word（.docx）导出为二期；PPT 仅预留 Schema，入口置灰
  • 版本管理：保存新版本、历史与差异对比、一键回退

7.3 审核（全局粒度，定稿）

  • 四动作：确认 / 修改（记录前后内容+原因）/ 驳回（记录原因与正确判断）/ 信息不足（记录缺失信息）
  • 全局审核 = 整份报告一个动作；修改时可改任何章节内容并填原因
  • 数据库保留 section_key 字段，未来可加逐条审核不需迁移
  • 注：审核四动作 + 案例四状态的产品细节当前暂缓讨论，搭建时先做数据结构支撑，界面后置

八、数据层（定稿）

  • 预置版本化模拟数据（sim_version）：开发、评测、上线演示共用同一批；部署后平台预置这批数据，不是空的
  • 时间跨度：每客户 45~55 天连续日数据
  • 场景注入（参数化，非随机）：50 客户中分布正常客户、单点异常客户、复合异常客户、数据缺失客户；注入参数（客户/日期/指标/幅度）可控可复现，评测能对答案。注意：这是数据构造的测试覆盖，与已简化的异常标签系统是两回事
  • 禁止诊断时临时随机生成数据；任何诊断只读固定版本快照
  • 数据双通道：①预置模拟数据 ②测试用户上传（页面"导入数据"入口，CSV/表单，面试演示用）；统一入 daily_metric 表，来源字段区分；上传数据同样过完整性检查；监控扫描两者
  • 已砍掉（不做）：数据源抽象层、真实广告 API 接入（对纯展示 Demo 属过度设计）

九、Agent 设计（定稿）

9.1 选型与约束

  • LLM：DeepSeek（已有 API key）；单次诊断 LLM 调用上限 ≤10 次
  • 编排：自研轻量 Python 节点图（不用 LangGraph/LangChain）；单 Agent，无多 Agent
  • 分工：代码 = 确定性（查询/计算/规则/权重/拆分）；LLM = 推理（下钻决策/归因解释/案例比较/建议生成）；LLM 永不心算，数字一律来自工具
  • 安全边界：工具目录不含预算修改、计划启停、账户操作；首期只读诊断
  • 全量 Tracing：每个工具调用（参数/结果/耗时/成本）落库 agent_tool_call

9.3 主链节点（10 个）

节点处理停止/失败条件
0 初始化校验客户与周期客户不存在/周期非法 → 失败
1 数据完整性检查check_data_completeness缺失严重 → 降级"数据不足"，不打硬结论
2 全面扫描固定扫版位/计划/笔记/漏斗不可跳过，每层产生状态与证据
3 分层诊断周环比+目标差距每层输出 正常/轻微/显著/数据不足
4 异常识别排序detect_anomalies + 权重Top3 进重点，其余观察项
5 异常下钻先串联后并联，LLM 决定顺序与深度充分证据 / 只能形成待验证项 / 轮次上限
6 案例检索比较search_cases + LLM 差异判断明确相似点与关键差异；Badcase 不可引用
7 建议生成绑定 8 条映射规则具体、可执行、带风险与预期观察指标
8 证据校验verify_evidence未过校验 → 回退修改或降级为假设
9 报告生成assemble_report进入人工审核

9.4 Prompt 开发流程

手写第一版 System Prompt → 模拟数据试跑 → 人工审查（幻觉/错误归因/不可执行建议）→ 修改迭代 → 3~5 个典型场景干净跑通 → 封装为可复用模块。

十五、暂缓与不做清单

  • 暂缓：审核四动作与案例四状态的产品细节；告警推送（最多后加站内通知）；Word 导出；逐条审核（结构已预留）
