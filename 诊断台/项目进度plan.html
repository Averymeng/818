一、你刚问的三个问题（先直接答）

1. badcase 什么时候做？是现在评测的 badcase，还是上线后积累的？

两头都有，但性质不同，归宿都是「案例库」。

  • 评测期 badcase（已做且闭环）：我们靠评测 + 你的逐份人工审，已经挖出 3 个智能体缺陷——①周值/日值混淆 ②建议依据数字不可核验 ③观察清单漏项（码上 feed 超目标没进清单）。另外 judge 校准期还有若干评分分歧。这些就是第一批 badcase，已经通过 system prompt 第 7 节红线修掉，相当于「已知缺陷已清除」。
  • 上线后 badcase（待积累）：真实用户使用踩的坑，持续进独立的 diag_badcase 库，再反哺评测和 prompt（参考案例库 diag_case 只放可引用的好案例，不混 badcase）。这是长期滚动的部分。
  • 结论：badcase 不是「以后才做」——评测发现的缺陷就是现在的 badcase，且已修。Phase 1 把这批评测缺陷固化为独立 badcase 库（diag_badcase）的首批条目（不与参考案例库 diag_case 混放），上线后继续长。

2. system prompt 有没有迭代？怎么迭代的？

迭代过，而且完全是被评测/人工审驱动的，不是凭空改文案。git 历史能看到清晰的 4 步：

提交版本做了什么
a2133e7v1 初版14 工具 + 10 节点编排 + 初版 prompt（dry-run 验证）
82f93a0v1.1§3.5 内联 8 条指标映射规则 + §7 钉死扁平输出结构
14c7c0d旧账修复案例章节透出、止损线数字、素材归因标注
7296e82v2 红线第 7 节加「周值/日值」「命名一致」「口径标签」「因果推断标注」「持平措辞」等硬红线

迭代方法（核心经验）：每发现一个真实翻车案例 → 把它转化成第 7 节一条显式红线（硬性约束）。因为 LLM 只能靠系统提示里的明红线约束，靠「语气/建议」没用。所以第 7 节是system_prompt.md 里唯一「只能加、不能删」的区——它是反复试错沉淀的护栏。

3. 真实数据接入 / 定时模拟 —— 现状是什么？

你没记错，我之前确实提过「可以用定时任务模拟实时更新」。但现状是还没落地：

  • 当前数据：智能体读 data/ad_review.db（sqlite），数据是 eval/seed_cases.py 灌的仿真数据。grep 确认仓库里没有任何 scheduler / 定时代码。
  • 模拟实时（过渡方案）：加一个定时任务（系统 cron 或 Python APScheduler），周期性重灌/拉取数据，让 DB 看起来「在更新」。这块代码还没写。
  • 数据本质：全部是系统自生成的模拟数据（seed_cases.py 造数），不存在外部真实数据源——我之前 plan 里写「真 API 需要你提供投放后台数据出口」是错的，已删。
  • 所以「定时模拟」就是自动端：加个定时任务（cron / APScheduler）每天 8 点周期重灌，演示「数据在更新」，不需要任何外部账号。
  • 但光看 AI 造的模拟数据，用户没有真实体感。因此 Phase 2 还要做手动录入入口：用户能复制粘贴（CSV/JSON 或填表）自己的真实投放数字进库，甚至新增数据表；报告生成不区分来源，谁灌进去就按谁算。这才是「能自用」的真产品体验。

三、阶段路线图（Phase 0 ~ 4）

0
基础闭环已完成

智能体核心 + 数据层 + 三层评测 + CI。等于「能出报告，且质量有自动保障」。

1
案例库 + RAG + 独立 badcase 库已完成

两块：①参考案例库（RAG 源）= diag_case 表（纯 referenceable=1 可引用好案例，已 seed）；语义检索工具 search_cases 已实现（按行业/赛道/品类/signature 召回，自动过滤 badcase）。②badcase 库（独立）= 新建 diag_badcase 表，与参考案例库物理分离：每条 = 错误输出 + 根因 + 对应红线修复 + 关联评测用例 + 状态。评测期 3 个智能体缺陷经 data/seed_badcase.py 首批入库。价值：badcase 库驱动 prompt 迭代与评测回归，形成「踩坑→修→防复发」飞轮。

2
数据层：定时刷新 + 手动录入部分 · 手动录入后端已完成

两部分：①自动端（未开始）——数据由 seed_cases.py 自己造（无外部真数据源），加定时器（cron / APScheduler）每天 8 点周期重灌，演示「数据在更新」，无需任何账号。
②手动端（后端已完成）——data/ingest.py 已实现：客户在前端页面小入口或直接编辑与前端绑定的本地数据表添加数据；字段不变（沿用现有 customer/daily_metric/plan/note 等表结构，只增数据行，不动态建表），daily_metric 写入标 source='upload'。入口 UI 归 Phase 3 前端。报告生成不区分来源。这是把「只能看 demo」升级成「能自用」的关键。

3
前端页面未开始 · 最后做

周报可视化展示 + 交互。放最后是因为后端稳了再做界面性价比最高，避免反复改。

4
上线 + badcase 闭环未开始

真实用户踩坑进案例库 → 反哺评测与 system prompt，形成「用得越多越准」的飞轮。这是长期运营阶段。

五、风险 / 待你确认

  • 数据本质：全部为系统自生成的模拟数据（seed_cases.py），不存在外部真实数据源，因此 Phase 2 是「自生成 + 定时刷新 + 用户手动录入」，不是「接入真实 API」。这点已按用户纠正修正。
  • 手动录入范围（已定）：客户在「前端小入口」或「直改与前端绑定的本地表」添加数据，字段不变、只增数据行，不动态建表。复杂度低，MVP 直接做。
  • RAG 是否必要：当前案例量很小（评测 24 条 + 缺陷 3 条），先用简单 SQL 匹配即可，上向量检索可等案例量起来再做——这条可按你判断取舍。
  • 前端范围：是纯展示周报，还是要交互（改参数重算、对比多周）？范围影响工期，需你定。
