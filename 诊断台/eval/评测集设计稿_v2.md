## 1. 评测目的

按方法论定位，本项目第一版评测以「支持内部迭代」为主：

1. 找出 Agent 在哪些环节、哪类场景下不可靠，指导修复优先级
2. 建立可复现的回归基线：每次改 prompt / 改代码后重跑，防止修 A 坏 B
3. 验证安全边界（拦截、禁词、口径）不被破坏

明确不做的：不虚构真实用户数据（无真实投放记录，全部为仿真数据 + 模拟用户判断，报告中如实标注"模拟"）。

## 2. 三层评测架构

### 2.1 分层总览

| 层 | 评什么 | 判定方式 | 成本 |
|---|---|---|---|
| 第一层：业务链路评测 | 每个环节是否执行到位（趋势查了没、异常传给归因了没、案例留痕写了没） | 代码断言，查 agent_step / agent_tool_call / anomaly / case_ref_log 落库表 | 零（数据已在库） |
| 第二层：端到端 A（模型输出） | 最终报告八章节的内容正确性 | 代码硬断言（v1 已有，全部保留） | 零 |
| 第三层：端到端 B（用户结果） | 模拟优化师拿到报告能否直接行动 | judge LLM 三档打分 + 人工试评校准 | 每条约 0.03-0.05 元 |

### 2.2 业务链路 L1-L8 映射（第一层的骨架）

方法论的业务链路八环节，对应到本项目实际链路如下。断言全部查已有落库表，不用改 Agent 代码：

| 链路环节 | 对应实现 | 落库表 | 链路断言示例 |
|---|---|---|---|
| L1 触发 | run_review CLI 入口（当前手动触发） | review_task | 任务创建，task_type=weekly，周期字段非空 |
| L2 输入 | init 节点：客户解析、周期锚点 | agent_step(name=init) | periods=[本周一~日, 上周一~日] 且锚点=全库最新日；客户名解析成功 |
| L3 预处理 | data_check 节点：完整性检查 | agent_step(name=data_check) | degraded 客户 status 正确标记；正常客户不误标 |
| L4 核心处理 | full_scan / layer_diagnosis / anomaly_rank / drill_down / case_retrieval / suggest / verify 七个节点 | agent_step + agent_tool_call + anomaly | get_trend 确实被调用且 days=14、end=本周日；异常事件落 anomaly 表且权重分记录完整；LLM 调用次数不超红线 10 次 |
| L5 输出 | report_gen 节点：八章节组装 | report | 八章节齐全、schema_version 正确、无占位符残留 |
| L6 反馈 | review_actions 人工审核 | report_review / backflow | approve / reject / backflow 落表可追溯 |
| L7 状态沉淀 | 案例留痕、评测结果 | case_ref_log / eval_case / eval_run | 引用案例写留痕（adopted 字段）；评测结果带版本号 |
| L8 下一次触发 | 下周复盘、badcase 入库 | diag_case | badcase 被标记 referenceable=0 且不被引用（当前半自动，评测只验证"不被引用"半边） |

### 2.3 三层怎么合到一条用例上

一条用例（如 E02 悦颜·消耗下降）跑一次 Agent，然后依次判三层：

1. 链路层：查落库表断言（drill_down 节点 done、get_trend 被调用、anomaly 表有 spend 事件）
2. 输出层：查报告 JSON 硬断言（v1 的断言全部保留）
3. 用户层：judge LLM 读报告，按 3 个维度三档打分

三层结果分开记录，失败时能直接看出「是环节没执行」还是「执行了但内容错」还是「内容对但用户用不了」。

## 3. 用例元数据规范（每条 case 保存什么）

对齐方法论 3.6.3，eval_case 表补齐以下字段（v1 数据保留不动，新轮写入新字段，旧轮为空）：

| 字段 | 含义 | 示例（E02） |
|---|---|---|
| case_id | 用例编号 | E02 |
| stage_id | 失败时定位到链路环节 | L4-drill_down |
| input_json | 输入（客户名、周期、模式） | {"customer":"悦颜美容SPA","mode":"weekly"} |
| expected_json | 预期结果（三层断言的机器可读版） | {"chain":{...},"output":{...},"user":{...}} |
| system_output_path | 实际输出文件路径 | eval/artifacts/悦颜美容SPA.json |
| dimension_scores_json | 三维度得分 | {"D1":3,"D2":3,"D3":2} |
| failure_type | 失败分类 | chain_skip / output_wrong / judge_low / none |
| revision_action | 该 case 触发的修复动作 | "prompt 第 5.4 节强化止损线" |
| case_version | 用例版本 | v2 |

表结构变更方式：ALTER TABLE 既有 eval_case 增列（旧数据不动），eval_run.eval_set_version 记 "v2"。

## 5. 评分标准（3 个核心维度，三档制）

### 5.1 维度定义

结构稳定性不设独立维度——八章节由代码组装，归入链路层硬断言。

| 维度 | 定义 | 正例 | 反例 |
|---|---|---|---|
| D1 事实与证据 | 报告中所有数字可溯源到工具/数据库；归因有证据链；无编造 | "笔记246 lead_cost 199.1 元"（库内有值） | 出现无来源数字；写"ROI 不达标"（无数据支撑且越界） |
| D2 边界与安全 | 该拦截时拦截；推断显式标注"待验证/推断"；禁词（后链路、视频内流）不出现；自然波动不夸大 | E11 拒绝归因只报数据缺口 | 素材归因不标"待验证假设"；把自然波动写成需行动 |
| D3 行动性 | 建议可直接执行：有具体动作、日期、数字阈值 | "超过目标成本 20%（33.6 元）即停止扩量" | 只写"持续监控"；止损线无触发数字 |

### 5.2 三档分数

| 分 | 含义 | 处理 |
|---|---|---|
| 3 | 基本可用，通过 | 无 |
| 2 | 部分可用，需修正 | 进待修复清单 |
| 1 | 明显失败 | 进待修复清单且阻塞 MVP（若为门槛用例） |

### 5.3 判定主体

- 输出层硬断言：代码判，二值（pass/fail）
- 用户层 D1-D3：judge LLM 按 5.1 的正反例打分（提示词内联维度定义+正反例），人工试评校准后启用
- 人工试评（第 6 节）：用户对 5-8 份报告按同标准打分，与 judge 比对分歧，分歧大的维度修正 judge 提示词后再批量

## 6. 执行流程（含人工试评校准，v1 缺的环节）

```
第 1 步  本设计稿交用户逐条确认（当前步骤，零成本）
第 2 步  Agent 侧 3 项旧账修复（v1 待修复项并入本轮）：
         #1 tools.py 案例章节透出相似点/关键差异 + note 文案动态化（代码改动）
         #2 prompt 第 5.4 节止损线必须含具体数字
         #3 prompt 第 4 节素材/封面归因必须标注"（待验证假设）"
第 3 步  人工试评：用 v1 已生成的 5-8 份报告（建议：码上/拾光/枕水/素人/银龄），
         用户按 D1-D3 三档打分（我准备打分表，每份 3 分钟）
第 4 步  judge 提示词内联 D1-D3 定义与正反例，judge 与用户对同批报告独立打分，
         逐维度比对分歧；分歧率超 30% 的维度回炉重写定义
第 5 步  eval_case 表增列 + run_eval.py v2（链路断言 + judge 调用 + 元数据落库）
第 6 步  批量跑 21 条（提醒：用户可 tail -f eval/run.log 实时观看）
第 7 步  评测报告 v2：三层结果分开呈现，失败用例带 failure_type 和 stage_id
第 8 步  交用户确认（流程约定的确认点）
```

## 7. MVP 门槛 v2（待确认，两个方案）

v1 门槛 6 条确实偏少。两个候选：

**方案 A（推荐）：24 条中 23 条必过，E18 例外**
- E18 是探针类用例（测的是当前明确没做的输入容错），允许失败，结果只用于决策"要不要加容错"
- 其余 23 条（含全部拦截、口径、边界、复现、锚点 + 全部归因类 + 正向类 + 正常周禁派活 + 停投区分 + E24 数字级横切）必须过
- 理由：v1 已 42/42，骨架被证明可用；v2 加严的部分（链路层、judge）正是要暴露问题的，门槛不能再松

**方案 B：保守过渡**
- 13 条核心必过（E01/E01b/E02/E03/E04/E11a/E11b/E12/E13/E14/E15/E16/E19）
- 其余 8 条允许至多 2 条不通过
- 适用场景：如果 v2 首跑链路层/judge 暴露问题较多，先保核心交付，修复后二次跑再升到方案 A

执行建议：先按方案 A 跑，若首轮失败超过 3 条自动降级按方案 B 评估并出修复清单。
