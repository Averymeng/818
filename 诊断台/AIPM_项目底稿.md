## A. aipm-anchor（功能锚点）

### A.1 场景有效性（为什么是真的痛点）
- **核心用户**：广告平台商业化销售（服务客户的平台侧销售，非客户侧投手）。
- **核心任务**：定期（每周）为客户做投放复盘——跨层级查数（账户/版位/计划/素材/转化漏斗）、定位波动、解释原因、形成优化建议、制作对客材料、追踪效果。
- **痛点（来自 PRD §2.2）**：信息分散、诊断耗时、结论不稳定（不同销售经验差异大、归因缺证据）、材料重复（每周重做网页+PPT）、经验流失（修改/执行/效果无系统沉淀）。
- **结论**：高重复 + 需非确定性判断，是真有 AI 介入价值的场景，不是"为了用 AI 而用 AI"。

### A.2 AI 节点适配度（AI 插在哪）
| 能力 | 承担者 | 说明 |
|---|---|---|
| 指标计算与聚合（ROI/CTR/CPC/转化率/环比/分层汇总） | **代码** | 确定性计算，不下放 LLM |
| 基础异常识别（阈值/突变/缺失/目标偏离/对象差异） | **代码/规则** | 确定性 |
| 诊断规划与原因推理（下钻路径、可验证假设） | **LLM 驱动的 Agent** | 非确定性 |
| 历史经验召回 | **RAG** | 结构化案例库 |
| 案例差异判断（是否真可比） | **LLM** | |
| 证据校验（事实/推断/建议分离） | **规则 + LLM 复核** | |
| 最终业务判断 | **商业化销售**（人工） | 审核/编辑/驳回/记录反馈 |

铁律（PRD §13）：确定性计算代码化；结论必须绑定数据证据；证据不足输出"待验证假设/数据不足"，不强行归因；不执行高风险账户操作（预算/启停/报价）。

### A.3 自进化 + 主动服务钩子
- **自进化**：审核（确认/修改/驳回/信息不足）+ 执行反馈 + 7 天后结果回流 → 沉淀为普通/已验证/标杆案例或 Badcase，用于优化规则、Prompt、评测集。案例达到 50–100 条后再考虑向量召回（早期用结构化筛选+LIKE）。
- **主动服务**：日监控异常提示（异常触发，不默认生成完整报告）+ 周度固定触发复盘任务；效果回看（观察期到达提醒）。MVP 已落地"周度触发 + 主动发起"。

### A.4 MVP 范围（已做 / 边界）
- **已落地（MVP 纵向闭环）**：选客户+周期→数据完整性检查→全层级扫描→分层诊断→异常排序→LLM 下钻→RAG 案例检索→建议生成→报告组装→事实校验→人工审核→案例沉淀。
- **边界（不进入）**：后链路（GMV/ROI/成交/有效线索）、素材生成、自动调预算/启停、完整 CRM、多角色权限、真实平台接口。RAG 不替代当前数据归因。

## B. aipm-chain（主链路 L1–L8）

```
L1 触发   ：周度固定触发 / 销售主动发起（选客户+周期）
L2 输入   ：客户周期数据（日度投放：消耗/曝光/笔记点击/按钮点击/私信开口/留资）+ 目标优化成本
L3 预处理 ：数据完整性校验（缺失/口径冲突显式提示）；周期对比（本周vs上周、昨日vs近14天日均、比例类近28天加权基准）；分层汇总
L4 核心处理（10 节点编排 Agent）：
   init → data_check(完整性) → full_scan(账户/版位/计划/素材/漏斗全层级)
        → layer_diagnosis(分层诊断, 每层 normal/异常/数据不足)
        → anomaly_rank(异常事件打四标签: 方向/形式/严重度/位置; Top3 重点, 权重 消耗40%/成本30%/幅度20%/置信度10%)
        → drill_down(LLM 下钻: 先串联漏斗定位环节, 再并联拆版位/计划/笔记; 输出假设+证据)
        → case_retrieval(RAG 结构化案例召回, 输出相似点+关键差异, 写入 case_ref_log)
        → suggest(建议: 依据/优先级/风险/观察指标)
        → report_gen(八章节结构化报告)
        → verify(事实校验: 结论是否引用数据, 区分事实/推断/建议)
L5 输出   ：八章节网页报告（封面/核心结论/指标与趋势/分层诊断/异常与原因/案例参考/优化建议/行动计划）
L6 反馈   ：人工审核（确认/修改/驳回/信息不足）→ 沉淀为参考案例 / 标记 Badcase
L7 状态沉淀：案例库（普通/已验证/标杆/Badcase）+ 追踪 + 评测 Badcase 回归
L8 主动触发：日监控异常提示 / 周度复盘任务 / 效果回看
```

**私信转化漏斗**（贯穿全链路的统一口径）：
曝光 → 笔记点击 → 按钮点击 → 私信开口 → 留资
- 优化目标为**开口**时看开口量/开口成本；为**留资**时看留资量/留资成本。
- 必须先沿漏斗串联定位问题环节，再并联拆版位/计划/笔记，禁止"看到留资降就断言话术问题"。

**业务层级**：行业 → 赛道 → 客户 → 品类（一个客户可经营多品类）。

## C. aipm-eval（评测体系）

### C.1 评测对象
- 链路节点：数据完整性判断、各层级覆盖、异常识别、下钻路径合理性、工具调用必要性、原因证据性（假设不伪装成事实）、案例相关性+差异准确性、建议具体可执行、报告结构完整、人工修改可追溯。
- 端到端：正常 / 单点异常 / 复合异常 / 指标冲突 / 数据缺失 五类场景可端到端跑通。

### C.2 评测集与执行
- **规模**：17 个主用例（E01–E17，含 E11 拆 a/b、E01b），自动化执行 **126 条断言，通过 126/126**。
- **评分**：MECE 分层 rubric（A 层硬断言 + B 层 LLM-as-judge 定性）；`judge_prompt.md` 校准，含 `judge_calibration_report.md`。
- **自动化**：`eval/run_eval.py` + GitHub Actions（`.github/workflows/eval.yml`）CI 回归。
- **Badcase 回归**：评测中发现的缺陷沉淀为 Badcase 用例，形成"低分→定位节点→修复→复测"闭环（已修复 2 类召回 bug：EN/CN 签名漏匹配、AND 过严导致空召回）。

### C.3 项目表达边界（必须守住）
- ✅ 可写：场景定义、报告/Schema 设计、AI 分工设计、评测体系设计、RAG 口径设计（归一化签名/去重）、部署方案设计、AI 协作落地。
- ❌ 不可写：独立写算法/模型 ownership、编造 GMV/AB 实验/真实用户量、把"模拟数据"说成"生产数据"、声称已上线真实平台。
- 模拟数据：可复现（按日期派生种子，禁止临时随机），约 51 客户 / 66 报告；**不是真实客户数据**。

## D. aipm-resume（简历贡献单元 + 事实映射）

### 贡献单元（建议简历条目骨架）
1. **定义场景与产品边界**：锚定"商业化销售周度复盘"高摩擦节点；与参考文档一致划定 MVP 范围与后链路边界。
   - 证据：PRD §2–§4、交接说明 §一。
2. **设计 AI 产品链路与分工**：以"代码/规则/LLM/RAG/人工"五分法明确各自职责，编排 10 节点 Agent 主链。
   - 证据：B 节主链路、orchestrator 10 节点。
3. **设计结构化复盘报告 Schema**：八章节报告（与 PRD §8.2 对齐），统一网页/PPT 同源。
   - 证据：8 章节 key、report 结构。
4. **设计 RAG 案例库与评测闭环**：归一化异常签名 + 去重口径；早期结构化检索（非向量）；沉淀 21 条参考案例；评测 126/126 驱动修复 2 类 bug。
   - 证据：diag_case=21、eval 126/126、召回修复。
5. **零成本落地与部署设计**：单 DeepSeek + 标准库、零第三方依赖；本地常驻（launchd）+ 静态只读快照（GitHub Pages）两种部署。

### 事实与边界说明（面试保命线）
- 代码由"我（产品设计）+ AI 编程助手"协作实现 → 体现 AIPM 的 AI 协作力，不谎称独立写算法。
- 数据为模拟（可复现）≠ 生产数据；产品为 MVP Demo，未接入真实广告平台。
- 评测 126/126 是"断言通过数"，非"用户量/业务指标"。
