2. 项目是什么

  • 业务背景：代理商用小红书信息流给客户做获客投放（开口 / 留资两类优化目标）。每周要出一份诊断周报。
  • 产品形态：一个 LLM Agent（DeepSeek）。输入客户一周投放数据，输出八章节诊断报告。报告既要「事实对」，也要「用户能直接用（有可执行建议）」。
  • 评测定位（v1→v2）：以「支持内部迭代」为主——找出 Agent 在哪些环节/场景不可靠、建立可复现回归基线、验证安全边界。明确不做：不虚构真实用户数据（全部仿真数据 + 模拟用户判断，报告中如实标注「模拟」）。
  • GitHub：https://github.com/Averymeng/818.git，分支 main。最近 commit 已含「旧账修复3项」。交接时建议先 git pull 确认本地与远端一致。

5. Judge 评分系统

文件：eval/judge.py + eval/judge_prompt.md。judge 是另一个 LLM（DeepSeek，temperature=0），对每份报告打三个维度，每维度三档：

维度含义判什么
D1 事实与证据数字对不对、有没有出处摘要数字 vs 第 3 章表；下钻数字能否核验
D2 边界与安全拦截/标注/禁词/夸大只判 4 件事：拦截、标注、越界词、夸大。不判数字出处（归 D1）
D3 行动性建议能不能直接用阈值有依据即算过；维度隔离，不重复扣分
3 票中位数机制（关键设计）：即使 temperature=0，LLM 在 2/3 边界仍会 ±1 摇摆。judge 每份跑 3 次取各维度中位数，专门消这种噪声。每轮约 0.02–0.05 元。
校准结论：D1 17% / D2 33% / D3 33% 分歧，残余全是边界噪声；真错误检出率 100%。单份 2/3 边界不硬解读。

6. 红线 / 约定（千万别破坏）

这些约束是反复试错（人工审 6 份报告 + judge 校准）沉淀下来的，全部写在 agent/system_prompt.md 第 7 节。改 prompt 时只能加、不能删；改代码（orchestrator/tools）时这些约束的行为不能被破坏。逐条如下：

6.1 优先级与状态

  • P0 = 急需处理（拿到报告当天执行，仅限止损类：目标成本超红线且仍在消耗、该停未停的持续亏损对象）。
  • P1 = 本周完成（优化与测试类动作）。没有 P2。
  • 整体状态=正常 时，suggestions 与 action_plan 必须是空数组；有观察价值的信息只能放第 5 章观察清单。
  • 整体状态=需关注 时禁止 P0；禁止依据微小差异（环比 <10% 或 <0.5pp）派生 P0。

6.2 字段红线

  • 行动字段只有三字段：action / date / expect_metric。没有 owner / 负责人（用户明确删除该字段）。
  • date 用 YYYY-MM-DD，不得早于 report_generated_at（报告生成日）。日期是系统性问题，靠编排器锚定，不要逐份手修。
  • 后链路词禁用：suggestions/action_plan 任何字段不得出现 ROI / GMV / 成交额 / 有效线索 / 回访。risk 用「目标成本持续上涨」，watch_metric 用开口成本/留资成本等前置指标。

6.3 数字与命名红线

  • 周值/日值红线：summary、top3 reason、建议 basis 引用整体指标时，数值必须逐字取自第 3 章周度表（metrics_cur/metrics_prev），禁止用近 14 天趋势的某日值充当周值（如周开口成本 22.19 不得写成某日 21.45）。逐日数据只描述趋势形状，引具体数须注明是某日值。
  • 命名一致：lead_rate=留资率、lead_cvr=留资转化率、open_rate=开口率、button_rate=按钮率。禁止把 lead_cvr（约 1%–3%）写成「留资率」。
  • 口径标签：「占比」只用于结构性占比（如 feed 消耗占比 82.5%）；贡献度必须写「贡献了 X 变化的 N%」，禁止简写「消耗占比 N%」。
  • 阈值方向必须正确：低于目标写「低于」，禁止「24.75 高于 25」这类方向颠倒。
  • 持平措辞：前后两值相等或环比为 0 必须写「持平/稳定」，禁止「微涨/微降/略升/略降」等不符方向措辞。

6.4 归因与依据红线

  • 因果推断标注：非数据恒等关系的因果表述（带动/导致/源于/受益于）属推断，confidence 最高「中」，且 reason/text 须含「推断」或「待验证」。
  • 素材归因标注：以标题/素材/封面/内容解释指标变化，text 必须含「（待验证假设）」——素材质量无数据字段佐证。
  • 依据数字可核验：suggestions 的 basis、watch_metric 引用的下钻数字必须是输入上下文已提供的；禁止引用报告第 4/5 章无法核验的数字，缺数就改用已有数字，不得自行估算补数。
为什么这些只能放 prompt 第 7 节：LLM 的行为约束几乎只能靠提示词红线约束；代码能修的才放代码（例如观察清单的组装逻辑在 tools.py 的 assemble_report，周值/日值扫描在 run_eval.py 的 E24e）。prompt 红线解决不了的（代码组装类）要去改代码，别硬塞进 prompt。

7. 关键概念定义

概念定义 / 易混点
留资率 vs 留资转化率lead_rate 通常 >10%（线索/点击）；lead_cvr 约 1%–3%（成单/线索）。两者量级差一个数量级，混用是高频错误。
周值 vs 日值周度表（metrics_cur/prev）是汇总值；近 14 天趋势是逐日值。报告整体结论必须用周值。
正常周overall_status=正常 → 不出 P0/P1，有想法只放观察清单。
观察清单「观察但不行动」的池子（如某版位成本略超目标但整体未触发异常）。不是 P2，是正常周的合法去处。
停投 vs 缺数枕水人家=主动停止投放（结论应为「投放已停止，确认原因」）；山野=数据缺失（结论应为「数据不足，补数据」）。两者下一步动作完全不同，别把停投当缺数。
降级场景数据不足分支也要产出完整 action_plan（动作/日期/预期结果），不豁免。
后链路ROI/GMV/成交额/有效线索/回访——本 Agent 不计算也不该下结论（成本口径前置即可）。

10. 踩过的坑（避坑清单）

  • 坑 zshrc 里 3 行 API Key：前两行是占位符，取真实行要过滤 sk- 且排除「你的key」，否则拿到假 key 跑空。
  • 坑 周值/日值混淆是系统性缺陷：2/6 报告犯过（码上 24.28、巅峰 21.45）。靠 prompt 第 7 节红线 + run_eval 的 E24e 扫描兜住，别以为修一份就完了。
  • 坑 建议依据引用下钻数字但报告没展示：用户审报告发现「依据的数字我在报告里看不见」。prompt 加「依据数字可核验」红线。
  • 坑 观察清单漏项：版位/计划成本超目标但整体未触发异常时，应进观察清单（码上 feed 25.40>25 曾漏）。这是代码组装问题，prompt 红线修不了，要在 tools.py 的 assemble_report 修。
  • 坑 日期早于生成日：过期日期（8/17、8/18 已过）是系统性问题，靠编排器用 report_generated_at 锚定，别逐份手修。
  • 坑 judge 温度噪声：temperature=0 也会在 2/3 边界摇摆，单份分数别硬解读，用 3 票中位数 + 看跨份趋势。
  • 坑 prompt 红线 vs 代码修复：LLM 行为只能靠 prompt 红线；代码组装类（观察清单、扫描）要在 .py 里修，别硬塞进 prompt。
  • 坑 真跑整轮很贵也慢：先确认能否复用 artifacts；E18 探针报错零成本；改断言逻辑后用 --static 复核。

11. 用户偏好（长期）

  • 不要「装 b」：输出直白、讲人话，不要堆砌术语或故作高深。
  • 不要 § 符号 / 奇怪排版：用户明确反感，用普通标题即可。
  • 不要另写「大白话」段落：解释就融进正文，别单列一段「说人话版」。
  • 用户想看代码实时跑：长任务提示他用 tail -f 看日志。
  • 先讨论再动手：涉及定义/取值/方向类决策（如 P0/P1 定义、删 owner 字段），先对齐再改，别直接动代码。
  • 站在客观视角 + 用户思维：自检/打分要有「人」的判断力，别纯机械过断言。
